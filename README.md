# IBMS

**[바로 열기](https://mjkim84.github.io/IBCM/)**

현재 상태: 2026년 10월 15일 단계별 세로 업무 목록을 포함한 화면의 GitHub Pages 배포와 공개 주소 검증을 완료했습니다. 위 링크를 누르면 최신 앱이 열립니다.

IBMS(Infociz Business Management System), **인포시즈 비즈니스 메니지먼트 시스템**은 프로젝트의 사전 영업부터 검수와 종료까지 관리하는 업무 앱입니다. 단계 승인, 데이터 저장, 모듈 등록과 이벤트 전달이 실제로 동작하는 기본 골격입니다. 업무 모듈 30개와 공통 모듈 6개는 모두 **준비 중**이며 실제 회의록 생성이나 견적서 생성 기능은 이번 범위에 포함하지 않습니다.

정적 모드는 위 링크로 열며 설치가 필요 없습니다. 기록은 사용한 브라우저에만 저장됩니다.

서버 모드는 Python 서버와 SQLite 파일에 기록을 저장하며, 코드를 함께 제공하지만 이번에 배포하지 않습니다.

두 모드는 `public/`의 같은 화면을 사용하고 `IBCM_STORE` 저장소 어댑터만 교체합니다.

## 화면에서 사용하기

1. 위 링크에서 프로젝트를 선택하세요. 처음에는 B 제안과 견적 프로젝트와 D 수행 프로젝트가 하나씩 있습니다.
2. 상단에는 A부터 E까지 큰 단계 카드 5개가 선으로 연결되어 있습니다. 어느 카드를 눌러도 해당 업무 목록이 열립니다. 각 카드의 단계 문자와 업무 개수를 확인할 수 있고 현재 진행 단계와 미리보기 단계는 따로 표시됩니다. 휴대폰에서는 단계 영역을 옆으로 넘겨 볼 수 있습니다. **현재 단계로 돌아가기**를 누르면 진행 중인 업무로 돌아옵니다.
3. B 단계 프로젝트에서 **누구로 행동할지**를 영업으로 고르고 **다음 단계 승인 요청**을 누르세요. 이벤트와 아웃박스에 요청 기록이 생깁니다.
4. 총괄 임원으로 바꾸고 **승인**을 누르면 실제 진행 단계가 C로 바뀝니다. **거절**에는 사유가 필요합니다. D 단계 프로젝트에는 처음부터 승인 요청 하나가 있습니다.
5. 현재 단계의 업무 카드나 하단 공통 모듈을 누르면 준비 중 안내가 나타나고, 실행 기록과 이벤트가 남습니다. 화면을 새로 고쳐도 기록이 유지됩니다.

상단 단계 카드는 기본적으로 이름, 담당 역할과 업무 개수만 간단히 보여 줍니다. **확장**을 누르면 단계별 모든 업무의 번호, 이름과 담당 역할이 세로로 펼쳐지고 **접기**를 누르면 간단한 화면으로 돌아옵니다. 단계나 프로젝트를 바꿔도 선택한 보기 방식은 유지되며 화면을 새로 열면 간단한 보기로 시작합니다. 세로 목록은 업무의 완료 상태나 필수 실행 순서를 뜻하지 않습니다. 목록을 눌러도 단계를 조회하기만 하며 실제 모듈 이용은 아래 상세 업무 카드에서 처리합니다.

선택한 카드 아래에서 넓어지는 연결선과 배경이 해당 단계의 상세 업무 영역으로 이어집니다. 선택한 카드와 상세 영역의 배경은 은은하게 박동하며 단계 선택에 따라 함께 바뀝니다. 기기에서 동작 줄이기를 설정하면 애니메이션 없이 강조 색상만 표시합니다. 승인 영역은 연결선을 가리지 않도록 단계 카드 위에 표시합니다.

선택한 단계의 업무는 **영업**, **수행**, **관리**별 영역에 모여 있습니다. 각 영역에 프로젝트 담당자 이름과 업무 개수를 표시하며 영업은 보라색, 수행은 청록색, 관리는 주황색으로 구분합니다. 해당 단계에 업무가 있는 역할만 나타납니다. 글자 크기와 간격을 정리해 단계, 역할, 업무 이름을 순서대로 읽을 수 있게 했습니다.

공통 모듈 6개는 **어느 단계에서든, 함께 쓰는 도구**라는 별도의 회색 영역에 모았으며 회의록만 분홍색으로 강조합니다. 공통 모듈은 어떤 단계의 목록을 보고 있어도 확인할 수 있습니다.

단계 카드를 누르는 것은 업무 목록을 살펴보는 동작입니다. 실제 단계는 바로 다음 단계에 대한 승인으로만 바뀌며 건너뛰기나 되돌리기는 허용하지 않습니다. 승인 영역에는 현재 단계와 이동할 단계가 함께 표시됩니다. 요청 중에는 중복 요청을 막고 총괄 임원에게만 승인과 거절 버튼을 보여 줍니다. 거절 사유는 화면 안의 대화상자에 입력합니다. E는 마지막 단계입니다.

정적 모드 상단에는 **정적 모드, 이 브라우저에만 저장됨**이 표시됩니다. 다른 컴퓨터나 다른 브라우저의 기록과 공유되지 않으며 브라우저 데이터를 지우면 저장한 기록도 없어집니다. 서버 모드의 데이터와도 별도로 저장합니다.

슬랙, 노션, 이메일의 **전송 완료**는 모의 어댑터가 로그를 남겼다는 뜻입니다. 실제 외부 서비스에는 전송하지 않습니다. 역할 선택은 승인 규칙을 확인하기 위한 기능이며 로그인이나 실제 신원 확인 기능은 없습니다.

## GitHub Pages 배포

주 결과물은 GitHub Pages에서 여는 정적 앱입니다. `.github/workflows/pages.yml`이 `main`의 변경을 받아 정적 파일을 만들고 GitHub Pages에 배포합니다. 공개 사이트에는 서버 코드나 사용자의 데이터 파일이 포함되지 않습니다. 처음 접속한 브라우저에 가상의 시드 데이터만 생성됩니다.

처음 배포하기 전에 저장소의 **Settings**에서 **Pages**로 들어가 **Build and deployment**의 **Source**를 **GitHub Actions**로 선택해야 합니다. 이 설정은 자동 배포 파일만 추가해서는 활성화되지 않습니다. 설정 후 저장소의 **Actions**에서 배포를 실행하고 결과를 확인할 수 있습니다. 실제 공개 여부와 계정 플랜에 따라 Pages 사용 가능 여부가 달라지므로, 비공개 저장소의 공개 전환은 소유자의 확인 없이 진행하지 않습니다.

정적 결과물은 `docs/index.html`이며 `docs/.nojekyll`도 생성합니다. 화면 수정은 `public/`에서 하고 생성된 HTML을 직접 수정하지 않습니다. 개발자가 로컬에서 다시 만들 때는 다음 명령을 사용합니다.

```sh
.venv/bin/python -m portable.build
```

이 명령은 같은 화면과 모듈 목록으로 `IBCM.html`과 `docs/index.html`을 만들며 두 결과물의 내용은 같습니다. `IBCM.html`은 내려받아 브라우저로 여는 보조 결과물입니다. 빌드할 때는 새 임시 데이터베이스를 사용하므로 기존 `data/ibcm.sqlite3`나 브라우저의 기록을 읽거나 공개하지 않습니다.

## 기술 선택과 저장 구조

서버 언어는 Python을 골랐습니다. 음성 인식 라이브러리가 풍부해 다음 작업인 회의록 자동화를 같은 서버에 연결하기 쉽습니다. Flask는 작은 서버를 단순하게 유지해 주며, 화면은 HTML, CSS, JavaScript만 사용해 별도의 프론트엔드 프레임워크가 필요하지 않습니다.

저장소는 SQLite를 사용합니다. 서버에서는 `data/ibcm.sqlite3` 파일 하나가 주 데이터이고, 정적 모드에서는 sql.js로 같은 구조를 브라우저에서 처리한 뒤 localStorage에 저장합니다. sql.js와 필요한 실행 파일도 결과물에 포함되어 별도의 외부 CDN을 불러오지 않습니다.

화면의 모든 데이터 요청은 `public/store.js`의 `IBCM_STORE.request`를 통합니다. 서버 모드는 Flask API로 보내며 정적 모드는 `portable/runtime.js`가 브라우저 저장소에서 처리합니다. 화면을 두 벌로 관리하지 않습니다. Python 모듈의 실제 실행은 서버 모드에서 지원하며 정적 모드는 이번 범위인 준비 중 모듈을 처리합니다.

저장 단위는 두 모드에서 같습니다.

| 이름 | 보관하는 내용 |
| --- | --- |
| `projects` | 프로젝트, 현재 단계, 담당자와 외부 연결 ID |
| `stage_transitions` | 승인 요청, 결정한 사람, 결정 결과와 거절 사유 |
| `module_registry` | 모듈의 이름, 단계, 역할, 상태와 연결 예정 스킬 |
| `module_runs` | 모듈을 확인하거나 실행한 기록 |
| `artifacts` | 실제 모듈에서 만들어질 문서와 산출물의 위치 |
| `events` | 이벤트 이름, 내용, 행동한 사람과 시각 |
| `outbox` | 연결 대상, 이벤트 종류, 전송 상태, 시도 횟수와 로그 |

이전 저장 데이터에는 필요한 컬럼을 추가해 보존합니다. `module_registry.skill`, `events.actor`, `outbox.project_id`, `outbox.event_type`, `outbox.log`가 포함되며 기존 컬럼도 유지합니다.

```text

adapters/                    이벤트 전달 설정과 외부 연결 스텁
seed/                        가상 프로젝트와 초기 기록

docs/index.html              GitHub Pages용 생성 결과물

data/                        서버의 로컬 데이터, Git에 포함하지 않음
```

## 새 모듈 추가하기

새 파일 하나와 등록 한 줄로 연결합니다. 화면 파일이나 서버의 실행 통로를 수정할 필요가 없습니다.

1. `modules/sample_task.py`를 다음 내용으로 만듭니다.

```python
from modules.base import ModuleDefinition, planned_render, planned_run

module = ModuleDefinition(
    key="sample_task",
    name="연결 확인 모듈",
    category="common",
    stage=None,
    order=7,
    mainRole=None,
    description="새 모듈의 연결을 확인하는 카드입니다.",
    status="planned",
    skill=None,
    run=planned_run,
    render=planned_render,
)
```

2. `modules/registry.py`의 `MODULE_FILES` 괄호 안에 한 줄을 추가합니다.

```python
    "sample_task",
```

3. 서버 모드는 서버를 다시 시작합니다. 정적 모드는 빌드 명령을 실행하거나 `main`에 올려 자동 배포되게 합니다. 화면을 새로 열면 공통 모듈에 **연결 확인 모듈**이 나타납니다.

단계 업무라면 `category="stage_task"`로 설정하고 `stage`에 A부터 E 중 하나, `mainRole`에 `sales`, `delivery`, `pmo` 중 하나를 넣습니다. 공통 모듈은 `stage`와 `mainRole`을 `None`으로 둡니다. `key`는 중복되지 않아야 하며 영문 소문자로 시작하고 영문 소문자, 숫자와 밑줄만 사용합니다. `order`는 1 이상의 정수이고 파일 안의 객체 이름은 `module`입니다.

`skill`에는 연결 예정인 기존 스킬 이름을 넣고 없으면 `None`을 사용합니다. 제안서와 킥오프 패키지 및 종료 보고는 **PPT 장표 생성**, 견적서는 **견적서 생성**, WBS는 **WBS 생성**으로 표시합니다. 이번에는 모두 표시만 하며 실제로 연결하지 않습니다.

### 실제 기능 연결 규격

`modules/base.py`의 `ModuleDefinition`이 공통 규격입니다. `run`에는 비동기 함수를, `render`에는 카드에 표시할 `label`과 `description` 사전을 반환하는 함수를 넣습니다. 준비 중인 `planned` 상태에서는 `run`을 호출하지 않으며 기능을 구현한 뒤 `ready` 또는 `active`로 바꿉니다.

`run(ctx)`는 `ModuleResult(summary="처리 결과", artifacts=[...])`를 반환합니다. 산출물이 없으면 `artifacts`를 생략합니다. 산출물 사전에는 `kind`, `title`, `location`이 필요하고 `stage`의 기본값은 현재 단계, `version`의 기본값은 1입니다.

| `ctx` 항목 | 내용 |
| --- | --- |
| `project` | 현재 프로젝트 사전 |
| `stage` | 현재 진행 단계 |
| `actor` | 선택한 담당자의 `role`, `name`, `label` |
| `store` | 현재 실행의 SQLite 연결 |
| `emit` | `ctx.emit("이벤트 이름", {...})` 형식의 발행 함수 |

기존 코드와의 호환을 위해 `user`와 `db`도 유지하며 각각 `actor`와 `store`와 같은 값을 가리킵니다.

`server/runner.py`가 시작과 종료를 `module_runs`에 기록하고 반환한 산출물을 `artifacts`에 저장합니다. 산출물마다 `artifact.created`를 발행하고 마지막에 `module.executed`를 발행하므로 모듈에서 같은 기록을 중복으로 만들 필요가 없습니다. 준비 중 카드는 `skipped` 실행 기록과 해당 상태를 담은 `module.executed` 이벤트를 남깁니다.

모듈은 공통 실행 트랜잭션 안에서 동작하므로 직접 `commit`이나 `rollback`을 호출하지 않습니다. 오류가 나면 공통 통로가 부분 데이터 변경을 되돌리고 `failed` 실행 기록을 남깁니다. 외부 API 호출이나 파일 생성의 취소는 실제 모듈을 구현할 때 따로 처리해야 합니다.

### 파일 하나와 등록 한 줄 검증

별도 소스 복사본에서 위 예제 파일을 추가하고 `MODULE_FILES`에 한 줄을 등록하는 실험을 진행했습니다. 서버 API에 전체 모듈 37개와 공통 모듈 7개가 나타났으며 브라우저에서 새 카드의 준비 중 표시를 확인했습니다. 새 카드를 누르면 `skipped` 기록, `module.executed` 이벤트, slack의 `sent` 아웃박스와 콘솔 로그가 생겼습니다. 시험용 모듈은 실제 등록 목록에 남기지 않아 기본 모듈은 36개입니다.

## 이벤트 추가하기

모듈 안에서 다음과 같이 발행합니다.

```python
ctx.emit("minutes.created", {"title": "고객 요구사항 회의"})
```

서버의 다른 기능에서는 상태 변경 트랜잭션 안에서 `server.events.emit(db, project_id, event_type, payload, actor=...)`를 호출합니다. 이벤트 객체에는 `id`, `project_id`, `type`, `payload`, `actor`, `created_at`이 있습니다.

외부 어댑터에도 전달하려면 `adapters/__init__.py`의 `EVENT_ROUTES`에 다음 항목을 추가합니다.

```python
    "minutes.created": ("notion", "slack"),
```

전달 대상이 없는 이벤트도 저장합니다. 설정 변경은 서버 재시작 또는 정적 모드 재빌드와 배포 후 반영됩니다. 정적 빌드도 이 설정에서 전달 대상을 읽습니다.

| 이벤트 | 전달 대상 |
| --- | --- |
| `project.created` | notion |
| `stage.approval_requested` | slack |
| `stage.approved` | slack, notion, email |
| `stage.rejected` | slack |
| `module.executed` | slack |
| `artifact.created` | notion |

이벤트를 저장할 때 `pending` 상태의 아웃박스를 만들고 어댑터에 전달합니다. 성공하면 `sent`, 실패하면 `failed`로 바꾸고 시도 횟수와 로그를 남깁니다. 실패 건은 서버 시작이나 다음 변경 처리 시 총 3회까지 재시도합니다. 현재 어댑터는 콘솔 로그만 남깁니다.

## 어댑터를 실제 API로 바꿀 때

서버 모드의 `adapters/slack.py`, `adapters/notion.py`, `adapters/email.py`에서 `handle(event)` 구현을 교체합니다. 함수는 이벤트 객체 하나만 받고 성공하면 반환하며 실패하면 예외를 발생시킵니다. 앱 객체나 데이터베이스 연결을 전달하지 않으므로 나중에 n8n 같은 자동화 엔진으로 보내는 구현으로도 바꿀 수 있습니다.

아웃박스의 저장과 전송 상태 관리는 `server/events.py`가 담당합니다. 인증 정보는 서버의 환경 변수로 전달하고 정적 결과물에 넣지 않습니다. 실제 API를 연결할 때 이벤트 `id`로 중복 전송을 방지하고 별도 작업자로 전송을 처리하는 방식을 검토할 수 있습니다. 이번에는 실제 API 호출이나 별도 작업자를 추가하지 않았습니다.

## 서버 모드 개발 실행

정적 링크를 사용하는 사람은 이 절차가 필요하지 않습니다. 개발자가 서버를 고칠 때 Python 3.10 이상이 설치된 환경에서 저장소 폴더를 열고 실행합니다.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m server
```

브라우저에서 `http://127.0.0.1:8000`이 열립니다. 자동으로 열리지 않으면 주소를 직접 입력합니다. 종료는 `Control + C`이며 다음 실행에는 마지막 명령만 사용합니다. `--port 8001`로 포트를 바꾸거나 `--no-browser`로 브라우저 자동 열기를 생략할 수 있습니다.

서버의 데이터 파일 기본 경로는 `data/ibcm.sqlite3`입니다. `IBCM_DB_PATH` 환경 변수로 다른 경로를 지정할 수 있습니다. 파일 백업은 서버를 종료한 뒤 진행합니다. 실행 중에는 같은 폴더에 SQLite 보조 파일이 생길 수 있습니다.

## 나중에 서버를 웹에 올리기

이번에 서버 모드는 배포하지 않습니다. 실제 회의록 처리나 외부 서비스 연동을 개발한 뒤에는 Render나 Railway 같은 서비스가 GitHub 저장소의 코드를 읽어 서버를 실행하게 할 수 있습니다. 링크로 혼자 앱을 살펴보는 현재 단계에는 이 절차나 새 계정이 필요하지 않습니다.

Render를 사용할 경우의 설정 예시입니다. 서비스의 요금과 메뉴는 이용 시점에 확인합니다.

1. Render에서 **New**의 **Web Service**를 선택하고 GitHub의 `MJKIM84/IBCM` 저장소를 연결합니다.
2. 실행 환경을 **Python 3**으로 선택하고 **Build Command**를 `pip install -r requirements.txt gunicorn`으로 설정합니다.
3. **Start Command**에는 `gunicorn 'server.app:create_app()' --bind 0.0.0.0:$PORT --workers 1`을 설정합니다.
4. 데이터가 재배포 후에도 남도록 영구 디스크를 `/var/data`에 연결하고 환경 변수 `IBCM_DB_PATH`를 `/var/data/ibcm.sqlite3`으로 설정합니다.
5. 배포가 끝나면 서비스가 표시하는 웹 주소로 접속합니다. 실제 공동 사용을 시작하기 전에는 로그인과 권한 기능을 별도 개발합니다.

SQLite 파일을 임시 디스크에만 두면 서버 재시작이나 재배포 때 기록이 사라질 수 있습니다. 영구 디스크는 유료 플랜이 필요할 수 있습니다. Railway를 선택해도 GitHub 저장소 연결, 시작 명령 설정, 영구 볼륨 연결과 `IBCM_DB_PATH` 지정이라는 준비는 같습니다. 서버를 여러 복제본으로 늘리는 구성은 이번 SQLite 파일 방식에 포함하지 않습니다.

## 검증

서버 자동 검증 명령입니다. 임시 데이터베이스를 사용하므로 사용 중인 프로젝트 기록에는 영향을 주지 않습니다.

```sh
.venv/bin/python -m unittest discover -v
```

서버 자동 검증 36개를 통과했습니다. 시드, 순차 승인, 총괄 임원 결정, 거절 사유, 준비 중 실행 기록, 산출물, 이벤트 전달, 재시도와 기존 저장 데이터의 컬럼 추가를 확인했습니다.

화면 개선을 반영한 정적 빌드는 Chromium에서 기존 38개를 확장한 52개 브라우저 점검을 통과했습니다. 모든 단계 문자와 업무 개수, 단계 미리보기, 담당자 이름을 포함한 역할별 업무 영역, 조회 중 데이터 유지, 역할에 따른 승인과 거절 버튼 표시, 거절 대화상자, 승인 요청 중복 방지, 공통 모듈 기록과 키보드 조작을 확인했습니다. 320픽셀, 390픽셀, 768픽셀 너비에서 단계 영역을 옆으로 넘기는 동작과 화면 배치도 확인했습니다. 모드와 스킬 표시, 기존 저장 데이터의 마이그레이션과 SQLite 무결성도 정상이며 브라우저 오류와 외부 네트워크 요청은 없었습니다. `docs/index.html`은 점검한 `IBCM.html`과 내용이 같습니다.

이 환경의 브라우저 정책이 로컬 파일 열기를 막아, 브라우저 점검에서는 HTML 바이트를 테스트용 주소에 주입하고 네트워크를 끈 상태로 실행했습니다. 기존 서버 모드는 임시 데이터베이스와 실제 로컬 서버를 사용한 브라우저 점검 10개를 통과했습니다.

세로 업무 목록에는 별도 브라우저 점검 20개를 추가해 총 72개를 통과했습니다. 각 단계의 업무 이름, 등록 순서, 담당 역할이 저장소 응답과 일치하며 목록 클릭은 단계 조회만 바꾸고 저장 기록에는 영향을 주지 않습니다. 320px부터 1440px까지 화면 너비 6개에서 업무명 잘림과 페이지 넘침이 없음을 확인했습니다.

기본 보기와 확장 보기 전환, 상세 업무 연결선과 박동 배경을 추가한 빌드는 기존 회귀 52개와 신규 점검 66개를 합쳐 118개를 통과했습니다. 키보드 조작과 포커스, 단계와 프로젝트 변경 후 확장 상태 유지, 동작 줄이기 설정, 320px부터 1440px까지 연결선 위치와 가로 스크롤 대응, 저장 기록 유지와 브라우저 오류 없음을 확인했습니다.

개선한 공개 사이트는 [GitHub Actions 배포 #5](https://github.com/MJKIM84/IBCM/actions/runs/38665389567)에서 확인했습니다. 배포 후 GitHub 실행 환경이 실제 공개 주소에 접속해 HTTP 200 응답과 배포 파일의 바이트 일치를 검증했습니다. 클라우드 개발 환경에서는 해당 도메인 접속이 제한되어 있어 이 공개 접속 검증은 GitHub 실행 환경에서 수행했습니다. 이후 배포에도 같은 검증을 자동으로 실행합니다.

## 판단 사항

1. 현재 연결된 실제 저장소는 `MJKIM84/IBCM`이므로 기존 이름을 유지했습니다. 요청서의 소문자 `ibcm`로 임의 변경하지 않았고 공개 주소도 실제 저장소 이름인 `/IBCM/`을 사용합니다.
2. 명세의 JavaScript 형태 모듈 객체를 Python의 `ModuleDefinition`으로 표현했습니다. 음성 인식 기능을 같은 언어로 연결하기 위한 선택이며 `mainRole`과 `skill`을 포함한 규격은 유지합니다.
3. 실행 기록과 산출물 저장 및 완료 이벤트는 공통 실행 통로가 보장합니다. 개별 `run`은 `ModuleResult`를 반환해 같은 기록을 반복 작성하지 않게 했습니다.
4. 준비 중 카드도 동작 확인이 가능하도록 `skipped` 실행 기록과 해당 상태를 담은 `module.executed` 이벤트를 남깁니다.
5. 산출물이 여러 개이면 `module_runs.artifact_id`에는 첫 산출물을 연결하고 이벤트의 `artifact_ids`에는 전체 ID를 넣습니다.
6. 초기 승인 요청은 D 프로젝트에 두어 B 프로젝트에서는 새 요청부터 시험할 수 있게 했습니다. 이름과 고객사는 가상이며 실제 고객 데이터는 포함하지 않습니다.
7. 사전 영업과 C, D, E 단계도 눌러 볼 수 있게 해 달라는 후속 요청에 따라 단계별 미리보기를 추가했습니다. 실제 진행 단계와 실행 허용 여부는 승인 규칙을 그대로 따릅니다.
8. 정적 모드도 SQLite 데이터 구조를 사용하고 결과를 localStorage에 보관합니다. 화면은 하나로 유지하며 Python 모듈의 실제 기능은 서버 모드에서 확장합니다.
9. 외부 어댑터는 이벤트만 받고 공통 전달 통로가 아웃박스를 관리합니다. 현재 `sent`는 실제 외부 전송이 아닌 모의 처리 완료를 뜻합니다.
10. 후속 요청에 따라 앱 표시 이름을 **IBMS**, 한국어 이름을 **인포시즈 비즈니스 메니지먼트 시스템**으로 바꿉니다. 기존 링크와 브라우저 기록을 유지하기 위해 저장소 이름, `/IBCM/` 주소, 저장소 키와 환경 변수 이름 및 `IBCM.html` 파일 이름은 그대로 둡니다.
11. 화면 개선에서는 단계 흐름을 큰 카드로 표시하고 업무를 담당 역할별로 모았습니다. 단계 조회와 실제 승인 이동은 구분하며 기존 저장 형식과 공개 주소를 유지합니다.
